# 使用、升级与继续迭代

## 日常使用

在项目文件夹让 Agent 读取 `AGENTS.md`。配置示例只是模板；启用记录时复制到 `local/config.json`，明确自己的 `profile_id`。所有个人资料写在 `local/`；根目录的 `memory/`、`style-profiles/` 只保留空模板。

任何时候都可以告诉 Agent“这次不记”“关闭记录”。关闭后不继续写；用户要求清理旧记录时再按明确范围处理，不能因关闭开关自动删除。

## 从原压缩包升级

1. 保留旧包的完整副本，在新文件夹下载或克隆本项目。不要覆盖原包或既有项目规则。
2. 仅在用户明确要求迁移时，读取其指定的个人文件。创建当前身份的配置，再把原始资料复制到 `local/inbox/`，个人风格复制到 `local/style-profiles/{profile_id}.md`，原件不动。
3. 旧 memory 是累积日志；如需复盘，按原文逐条转换成 `local/sessions/{profile_id}/{session_id}.md`，保留原日期与源位置。无法确定是否同一期的条目先保留待核实，不凭 AI 摘要硬合并。旧“成稿”字段不能推出已拍或未拍。
4. 先做一条小测试，核对来源、身份和保存位置。无需读取或迁移其他成员资料。

原包内 dbskill 可本地继续使用，本项目不替它升级。`口播助手-进阶指令.jpg` 属于旧版指令图，使用方式以新版 README 为准。

## 拉取规则更新

```sh
git status --short
git pull --ff-only
python3 scripts/check_project.py --tracked
```

如果存在自己对规则的改动，先保存成提交或副本再合并。`--ff-only` 拒绝合并时，查明分支差异；不要使用强制重置覆盖工作。忽略的个人文件不会随拉取更新，但也不会被 Git 备份；个人资料应另行备份。

ZIP 升级使用“新文件夹 + 按需复制 local”方式。不要把整个旧项目复制进新目录，以免旧规则覆盖新版。Git 项目更新和可选依赖更新是两件事。

## 修改与提交

1. 先用一个实际问题说明需要改哪条规则，优先修最短的一段。
2. 修改主规则／模块，运行下面两项检查；涉及行为时再执行相关验收案例。
3. 在 `CHANGELOG.md` 写清前后行为，更新 `VERSION`。小修用补丁版本，兼容的新增功能用次版本，破坏兼容的变化用主版本。
4. 查看待提交文件，只加入规则、模板和工具。不要 `git add -f` 个人文件或原第三方整包。
5. 提交并推送。GitHub 自动检查通过后，核对远端提交与本地一致。

```sh
python3 -m unittest discover -s tests -v
python3 scripts/check_project.py --tracked
git diff --stat
git status --short
```

## 版本回看与回退

用 Git 历史查看某个版本改了什么；需要退回规则时，优先对相关提交做反向提交，保留历史。对尚未发布的本地修改，也先查看差异并保留副本。不要用清空目录或强制重置作为常规升级方式。

## 验证能证明什么

结构检查保护功能路径、链接、模板默认值和常见误上传路径，不验证事实与创作效果，也不能识别所有隐私。检查提交清单仍是维护步骤的一部分。[行为案例](../tests/scenarios.md) 要独立执行，保存脱敏输入与输出；不能把“规则里写了”当作模型已经做到了。
